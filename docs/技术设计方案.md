# dwgparse 技术设计方案

> 零依赖（纯 `std`）、从零实现的 DWG 解析器，锁定 **AC1015 / AutoCAD R2000**。
> 目标能力：图层信息、图元几何坐标、**扩展属性（EED + XData）**。
>
> 阅读顺序建议：第 0～1 章建立全局图景 → 第 2～4 章是格式与位流机制 → 第 5 章是三类
> 业务数据的解码 → 第 6 章是 API 调用范式（**日常使用只看这章就够**） → 第 8 章是踩坑清单。

## 第 0 章 设计目标与约束

### 0.1 需求拆解

| 需求 | 落到本方案的实现 |
| --- | --- |
| 最少引用依赖 | **零第三方依赖**，`Cargo.toml` 无任何 `[dependencies]`；只用 `std::{fs, collections::HashMap}` |
| 解析图层信息 | `LAYER` 表记录（类型码 `0x33`）：名称、颜色、冻结/关闭/锁定/打印/线宽、线型句柄 |
| 解析图元几何坐标 | 基础（LINE / CIRCLE / ARC / POINT / TEXT / MTEXT）、块参照（INSERT）、轻量多段线（LWPOLYLINE）、经典多段线（POLYLINE 2D/3D/MESH/PFACE 及链式 VERTEX）、曲线（ELLIPSE）、平面面片（3DFACE / SOLID / TRACE） |
| **解析扩展属性** | 两套机制都实现：**EED**（实体级扩展实体数据）与 **XData**（`XRECORD` 内的 resbuf 链） |
| 测试用例 | 位原语（19）＋解码纯函数（27）＋颜色（3）＋R2007 段（4）＋EED/XData（4）＋装配链字段流（9）＋端到端（11）＋实体扩展（8）＋不变量（4）＋鲁棒性（4）＋CLI（7）＋版本路由（5）＋真值核对脚本（6 fixture）＋**XData 跨版本核对（3）**＝ **112 个**（另加图层表 2），0 失败 0 警告 |

### 0.2 版本覆盖

| 内部代号 | 对应 AutoCAD 发行版 | 可否解析 | 说明 |
| --- | --- | --- | --- |
| AC1012 | R13 | 部分兼容 | 无 `nolinks` 等 R2000 字段，条件分支不同 |
| **AC1015** | 2000 / 2000i / 2002 | ✅ **完全支持** | 扁平段、对象按绝对偏移寻址，结构最清晰 |
| **AC1018** | 2004 / 2005 / 2006 | ✅ **支持** | **不是页容器**：以 12 字节 `AcFssFcAJMB` 标识串开头的**段树**，LibreDWG 单开 `r2004_header` + `decode_r2004`。本实现已实现该段树（`decode_R2004`） |
| **AC1021** | 2007 / 2008 / 2009 | ✅ **支持** | **唯一**使用页容器的发行版；字符串改走独立字符串流（UCS-2 `TU`）；页头有 `0x4164536b ^ address` XOR 掩码（见下） |
| **AC1024** | 2010 / 2011 / 2012 | ✅ **支持** | **复用 AC1018 的段树容器**，仅版本戳不同；对象字段另按 `EntityVariant::R2010` 裁剪 |
| **AC1027** | 2013 / 2014 / 2015 / 2016 / 2017 | ✅ **支持** | 同上，`EntityVariant::R2013` |
| **AC1032** | 2018 / 2019 / **2020** / 2021 / 2022 / 2023 / 2024 | ✅ **支持** | 同上，`EntityVariant::R2013` |
| AC1037 | 2024+ | ❌ **不支持** | 更新格式，无实测样本；**明确拒绝**，不做猜测解析 |

> **关键结论（已两次更正）**：容器只有**两套**，不是一套。AC1021 是唯一使用页容器（RS 去交织 ＋ LZ77）的发行版；AC1018 用的是**段树**容器，而 **AC1024 / AC1027 / AC1032 复用的正是这套段树**。
> 因此 `parse_file` 现在把 AC1018 / AC1024 / AC1027 / AC1032 路由到 `parse_r2004`（段树），只把 AC1021 路由到 `parse_r2007`（页容器）；R2000（AC1015）因段是**磁盘表示**走独立路径。实现 `decode_R2004` 因而一次性解锁了 R2004 / R2010 / R2013 / R2018–2024 四档。
>
> 早期版本先是把 AC1018 也算进"页容器"家族（错），后来改成前置拒绝（保守但正确）。现在它自己能解了——见下。
>
> 容器只是上半场：对象字段本身也按版本裁剪，见 0.2 末尾的"对象字段的版本闸门"。

#### "CAD 2020" 是哪一个代号？

**AutoCAD 2020 没有独立的文件格式**——它写出的是 `AC1032`。Autodesk 在 2018 引入"DWG 2018 格式"后一路沿用，2018 / 2019 / **2020** / 2021 / 2022 / 2023 / 2024 七个发行版共用同一个代号。所以"增加解析 CAD 2020"这个需求，等价于"支持 AC1032"，而 AC1032 已在放行列表内。

既然如此，"支持"就必须拿证据，而不是"版本串在一个 match 分支里"就算数。本项目改用**五份真实样本**验证（`tests/version_routing.rs`）：同一张图分别由 2004 / 2007 / 2010 / 2013 / 2018 另存，五档全部要求解析成功，且去掉字符串负载后的几何指纹排序后**逐位相等**。

> **"改戳法"已经退役。** 它曾经是这里的主力手段：把 AC1021 样本偏移 0 处的 6 字节改成
> `AC1032`，其余字节一字不动，断言两者输出位级一致。现在这个技巧**不再成立**——AC1021 走页
> 容器、AC1032 走段树容器，改戳只会因为容器不匹配而失败，说明不了任何关于版本戳的事。真样本
> 比它强得多，而且顺带覆盖了对象字段的版本闸门（见下）。

第 3 步仍是**位级**比较而非近似比较：`Geometry` 故意不派生 `PartialEq`（内含 `f64`，`==` 在
`NaN` 下甚至不满足等价关系），于是比较 `Debug` 输出——它以最短往返精度打印双精度。指纹只保留
坐标、标志位和顶点数，字符串负载被抹掉：这张图在两次另存之间被编辑过，2007 版存的是 MTEXT
`108\U+00B0`，2018 版存的是 `108°`（LibreDWG 的 `dwg2dxf` 导出一致）。

#### AC1018（R2004）为什么必须先单独拒绝、再单独实现 —— 一次横向联测抓出的真 bug

页容器不是 R2004 引入的，是 **R2007** 引入的。R2004 用的是另一套东西：文件头以 12 字节 ASCII
标识串 `AcFssFcAJMB` 开头，后面是 `root_tree_node_gap` / `lowermost_left_tree_node_gap` /
`lowermost_right_tree_node_gap` / `last_section_id` / `last_section_address` —— 一棵**段树**。
LibreDWG 为此单开了 `dwg->fhdr.r2004_header` 与 `decode_r2004`。

本实现早期把 `AC1018` 与 `AC1021` 并列写进 `parse_r2007` 的分支，于是：

* 拿真实 R2004 样本（`tests/data/example_2004.dwg`）来解，`decode_rs` 在 0x80 块上就吐出
  垃圾（`compr_len = 1330247314`），随后 LZ77 报 `decompression error: offset underflow`；
* 这个错误信息**指向压缩算法，而真因是容器选错**，排查方向完全被带偏；
* 更糟的是"改戳法"测不出来——把 AC1021 改成 AC1018 照样通过，因为解码器根本不看版本戳，
  它拿到的是一个货真价实的页容器。**只测合成样本、不测真实文件，就会漏掉这类问题。**

第一步修正：AC1018 单独一条 match 分支，前置拒绝并说明它用的是哪种容器。
第二步（本次）：真正实现 `decode_R2004` —— 140 字节 XOR 头 + ACD 自适应压缩 + 段页映射 +
段信息表。关键发现是 **AC1024 / AC1027 / AC1032 复用的正是这套段容器**，所以这一个实现同时
解锁了 R2004 / R2010 / R2013 / R2018–2024。回归测试从"必须被拒绝"改写为"必须解出图层名与
几何"，并与 LibreDWG 的 `dwg2dxf` 真值逐字段核对。

> 教训：版本闸门"放行"与"真的能解"是两件事。凡声称支持的版本，都必须有该版本的**真实样本**
> 兜底，否则就应该拒绝而不是放行。

#### 对象字段的版本闸门：容器对了还不够

容器解出来之后，2010 / 2013 / 2018 仍会解出垃圾几何——因为**对象字段本身也是按版本裁剪的**。
最容易踩的是 LibreDWG 的 `common_entity_data.spec`，它在四个版本边界上长过：

```text
SINCE(R_2004a)  AC1018+ : is_xdic_missing (B) 取代 nolinks；颜色改走 ENC
SINCE(R_2007a)  AC1021+ : material_flags (BB) + shadow_flags (RC)，以及"每对象字符串流"
SINCE(R_2010b)  AC1024+ : has_full / has_face / has_edge_visualstyle（各 1 bit）
SINCE(R_2013)   AC1027+ : has_ds_data (B)
```

少读一个 bit，后面每一个坐标都会整体位移——产出的是**看起来合理的垃圾**，不会报错。实测：
用 AC1021 的布局解 2004，坐标落在 bit 94 而真值在 bit 85；解 2010 则差 13 / 28 bit。
为此引入 `EntityVariant { PreR2004, R2004, R2007, R2010, R2013 }`，把它一路传进
`read_common_entity_fields` / `read_entity_common_handles` / `read_t` / `read_cmc`。

与之相关的第二颗雷是"字符串流"：**AC1018 没有字符串流**。LibreDWG 只在 `SINCE(R_2007a)` 分支
里调用 `obj_string_stream`，其余情况下 `Bit_Chain *str_dat = dat`；`bit_read_T` 的
`IS_FROM_TU` 判据是 `from_version >= R_2007`，所以 R2004 的图层名/块名/颜色名都是**字段流上的
内联 TV**。按 R2007 的方式去字符串流里取，结果就是空串——这一次表现为"每个实体的 layer 都是空"。

同一颗雷还顺带暴露了 `BLOCK_HEADER` 的字段流顺序：`num_reactors(BL)` 与
`is_xdic_missing(B, R_2004a+)` 属于通用的 `common_object_handle_data.spec`，在**字段流**上、
在任何对象自身的字段之前。R2007 之所以长期没暴露这个漏读，是因为 R2007 的对象名在**独立的
字符串流**上，字段流少读几位不影响它；R2004 的名字是内联的，于是立刻错位。

#### 对象（表记录）另有一套闸门：图层表的两个 1~2 bit 陷阱

实体几何全部对齐之后，图层表（LAYER，`0x33`）在 **AC1027 / AC1032 上仍然报出全表同值**
（五条图层一律 `color=97 lw=0`），而 LibreDWG 真值是 `62 = 7/2/4/7/7`、`370 = -3`。
直接翻 LibreDWG 的 `src/common_object_handle_data.spec` 与 `src/spec.h` 才定位到两处各差
1~2 bit 的闸门：

```text
common_object_handle_data.spec —— 对象在字段流上的序言
    num_reactors(BL)      SINCE(R_13b1)
    is_xdic_missing(B)    SINCE(R_2004a)
    has_ds_data(B)        SINCE(R_2013)   <- 漏掉它，AC1027+ 整表错位 1 bit

COMMON_TABLE_FLAGS（spec.h）—— 紧跟 name 之后
    UNTIL (R_2004)   : is_xref_ref(B) + is_xref_resolved(BS) + is_xref_dep(B)  = 4 bit
    LATER_VERSIONS   : is_xref_ref 派生为 1，只读 is_xref_resolved(BS)         = 2 bit
```

`has_ds_data` 之所以长期隐身：实体那一份由 `common_entity_data.spec` 提供，早已在
`read_common_entity_fields` 里读过，所以**几何交叉核对永远发现不了对象这一位**。

第二个更反直觉：**`UNTIL (R_2004)` 的 R_2004 是闭区间**，AC1018 仍走旧的三字段分支。
此前闸门写成 `variant >= R2004`，于是 AC1018 少读 2 bit，`flag0` 从真值 `0x3F0`
（plotflag + lineweight 31）读成 `0x3C`，CMC 颜色与线型句柄跟着一起错位。

两处都不能用"看起来合理"来判断，只能拿真值对齐：`tests/layer_table.rs` 对五档样本各 5 条
记录比对 DXF `2 / 62 / 370 / 70`；其中 AC1018 系统图层的 `70 = 5`（frozen + locked）、其余
各档为 `0`，正好是 `UNTIL (R_2004)` 分支的可证伪证据。

> **XData 已在全部六档（AC1015 / AC1018 / AC1021 / AC1024 / AC1027 / AC1032）上正确解出**，
> 不再只是 AC1015 单点钉死。修复了两处曾让现代文件串扰的真因：
>
> 1. **位偏移必须保留**：`decode_xdata` 末尾原本 `r.bit = 0` 把进入时的 bit 偏移抹掉，使非字节
>    对齐的 XDATA 区结束后游标少移 1 bit，连带其后的 `BS cloning`（DXF 280）整体错位。2007 样本
>    handle `0x26B` 修复前读出 `-24448`、真值 `1`。`bit_read_RC` 是按位对齐的——消费 8 位但保持
>    `bit` 不变，所以进、出 bit 偏移一致，窗口是纯字节窗口（与 LibreDWG `while (dat->byte < end_address)` 同构）。
> 2. **R2007+ 字符串走 TU（UCS-2LE）而非 TV（单字节）**：`decode_xdata` 现按 `Dialect` 选 TU/TV。
>    原来的 TV 读法把每个 UTF-16 单元的 `0x00` 高字节当成边界，字符串连后续二进制块（TF 311）一并错位；
>    2018 样本 handle `0x764` 现正确解出 `"BA881000-D789-5D94-D8B4-EEC8EF3D3BFF"`。
>
> 跨版本真值由 `tests/xdata.rs` 钉死：对 2004/2007/2010/2013/2018 五个现代样本的 `XRECORD`
> （handle `0x26B…0x270`）断言 `[270=Int16(1), 271=Int16(1), 280=Int16(1)]`，并断言 AC1015
> 的 `SHADEPLOT` 链与"每个现代样本至少 6 个非空 XData 对象"。AC1015 仍额外由 `tests/integration.rs`
> 断言 `SHADEPLOT` / `SHADEPLOTCUSTOMDPI = 300`。

#### 为什么 R2007+ 版本无关？三个"看起来会分叉"的地方都绕开了

LibreDWG 里确实存在与版本相关的条件分支，但它们都不落在我们的解码路径上：

| LibreDWG 分支 | 位置 | 我们是否受影响 |
| --- | --- | --- |
| Classes 段多读一个 `RL hsize`（`version >= R_2010 && maint > 3 \|\| >= R_2018`） | `decode.c` 读 CLASSES | ❌ 不受影响 —— 我们不解析 Classes 段 |
| 段级字符串流起点 `start = bitsize + 159`（R2007）对 `+ 191`（R2010+/R2018） | `decode_r2007.c: section_string_stream` | ❌ 不受影响 —— 我们只取 `objects` / `handles` / `classes` 三段，不用段级字符串流 |
| 数据页 32 字节页头 XOR 掩码 `0x4164536b ^ address` | `decode.c: read_2004_compressed_section` | ❌ 不受影响 —— 我们不解析页头，`comp_size` / `uncomp_size` 直接从段映射取 |

第三点顺带解释了本实现为何不需要实现那个 XOR 掩码：掩码只作用于 32 字节页头，而页头唯一的作用就是告诉解码器压缩前后尺寸——我们已经从段映射里拿到了。

R2000 仍是"最易读懂"的一档；本方案已越过页容器这道坎，把 R2007–2024 一并拿下。
`parse_file` 仍在最开始校验版本串，对未知版本直接报错，避免"读出来一堆垃圾却看起来像成功"
——对 AC1032 之后的 AC1037、以及容器不同的 AC1018，同样如此。

### 0.3 非目标（明确不做）

* 不写 DWG（只解析）；
* 不做坐标系/视口变换、不渲染；
* 不解析 BLOCK 内部的嵌套图元归属树（见 [9.2](#92-演进路线)）；
* 不支持加密/受保护图纸（CRC 校验失败即拒）。

## 第 1 章 一页纸总览：从字节到结构化数据

### 1.1 解析管线

```text
 ┌────────────────┐
 │ 文件头 (0..25)  │  版本串 "AC1015" —— 第一道闸门
 └───────┬────────┘
         ▼
 ┌────────────────┐
 │ 定位表 §0..§5   │  6 × (RC number, RL address, RL size)，大端
 │ 起于 byte 25    │  → 取出 §2 = Handles（对象映射表）
 └───────┬────────┘
         ▼
 ┌────────────────────────────────────────────────────┐
 │ 句柄段（对象映射表）                                  │
 │ 分页链：RS_BE 页大小 → (UMC 句柄增量, MC 偏移增量)*   │
 │         → 字节对齐 → RS_BE CRC → 下一页              │
 │ 产物：每个对象记录的**绝对文件偏移** offsets[]         │
 └───────┬────────────────────────────────────────────┘
         ▼  对每个 offset
 ┌────────────────────────────────────────────────────┐
 │ 对象记录：MS size → BS type → RL bitsize → 字段数据  │
 │                                    → 句柄流         │
 │  · 字段数据 rd：几何/名称/标志；按类型分派解码器      │
 │  · 句柄流   hr：owner/reactors/xdict/layer/ltype/…  │
 └───────┬────────────────────────────────────────────┘
         ▼
 ┌────────────────────────────────────────────────────┐
 │ 后处理：handle→index 索引、收集 layers、             │
 │         BLOCK_HEADER 句柄→块名，回填 INSERT.block_name│
 └───────┬────────────────────────────────────────────┘
         ▼
      DwgFile { version, layers, objects, handle_index, block_names }
```

### 1.2 产物（五类）

| 产物 | Rust 类型 | 来源 |
| --- | --- | --- |
| 图层表 | `Vec<LayerInfo>` | 类型码 `0x33` 的对象 |
| 图元几何 | `ParsedObject.geometry: Option<Geometry>` | 实体类型 `0x01/0x07/0x11/0x12/0x13/0x1b/0x4d` |
| 实体级扩展属性 | `ParsedObject.eed: Vec<Eed>` | 每个对象自身句柄后的 EED 链 |
| XData 扩展属性 | `ParsedObject.xdata: Vec<XDataItem>` | `XRECORD`（`0x4f`）对象 |
| 块定义与引用 | `ParsedObject.block_name` / `block_handle` | `BLOCK_HEADER`（`0x31`）＋ `INSERT`（`0x07`） |

## 第 2 章 文件结构（由外到内）

### 2.1 文件头

```text
offset 0x00 : 6 字节 ASCII 版本串   → "AC1015"
offset 0x06 : 5 字节 0x00
offset 0x0B : maintenance byte
offset 0x0C : 1 字节 0x00
offset 0x0D : RL image seeker（缩略图偏移，通常为 0）
offset 0x11 : 若干未知/保留字节
offset 0x19 : 定位表开始（十进制 25）
```

`parse_file` 只做三件事：读前 6 字节校验 `"AC1015"`、拒绝小于 30 字节的文件、然后从 25 起读定位表。

### 2.2 定位表（Section Locator）

R2000 有 **6 条**记录，每条 9 字节，`RL` 为**大端**：

```text
RC number      (1)
RL address     (4, big-endian)
RL size        (4, big-endian)
```

| § | 含义 | 本解析器是否使用 |
| --- | --- | --- |
| 0 | Header（类定义头） | 否 |
| 1 | AuxHeader / R2004+ 才有 | 否 |
| **2** | **Handles（对象映射表）** | **是 —— 对象入口全靠它** |
| 3 | Template | 否 |
| 4 | ObjFreeSpace | 否 |
| 5 | 未知/保留 | 否 |

> 关键认识：**对象不是顺序排列的**，也不能靠"扫全文件找记录"来定位。必须先读 §2 拿到偏移表。
> 后续 R2004+ 的 §2 需要解密，本方案不涉及。

### 2.3 句柄段（对象映射表）

段内是**页链**，页结构与 LibreDWG `decode.c` 的 `handles_section:` 循环一致：

```text
do {
    startpos     = byte
    section_size = RS_BE                  // 含自身 2 字节
    while (byte - startpos < section_size) {
        handleoff = UMC                   // 句柄增量（本方案不需要）
        offset    = MC                    // 有符号地址增量
        last_offset += offset             // → 一个对象的**绝对文件偏移**
    }
    if (bit > 0) byte += 1                // 补齐到字节边界
    crc = RS_BE                           // 页校验（本方案跳过内容，仅推进游标）
} while (byte < map_end && section_size > 2)
```

实现要点（`src/parser.rs::parse_handles`）：

* `section_size <= 2` 视为空页并结束；`> 2040` 视为损坏并结束（LibreDWG 的规则）；
* CRC 前必须**字节对齐**，否则后续页全部错位；
* `last_offset` 为 `i64`，因为 `MC` 是**有符号**增量，前一页可能回落；
* 加三道防御：偏移必须落在文件长度内、`r.byte == oldpos`（无进展）立即跳出、越界即停。

### 2.4 单个对象记录

```text
┌────────┬──────────┬─────────────┬──────────────────────────┬────────────────┐
│ MS size│ BS type  │ RL bitsize  │ 字段数据（field data）    │ 句柄流（handles）│
└────────┴──────────┴─────────────┴──────────────────────────┴────────────────┘
   变长      变长        4 字节       bitsize 位               直到 size 结束
```

* `size`：对象记录总字节数（含自身）；
* `bitsize`：**自对象数据首字节起的位偏移**，指向句柄流起点 —— 因此它**包含头部自身的位宽**
  （实测：`type` 用 8 位值紧凑 `BS` = 10 位 ＋ `bitsize` 32 位 = **42 位头部**）；
* 句柄流起点 = 对象数据内 `byte = bitsize/8, bit = bitsize%8`；
* R2000 对象流**未压缩**，所以 `size` 之后就是明文位流。

> 这意味着**每个对象都可以独立解析**：只要偏移对，就能单独解码。解析天然可并行（当前实现是串行的）。

## 第 3 章 位级读取原语

DWG 是**位导向**格式，不是字节对齐格式。整个解析器的地基是 `src/bitreader.rs::BitReader`：

```rust
pub struct BitReader<'a> { data: &'a [u8], pub byte: usize, pub bit: u32 }
```

约定（与 LibreDWG `bits.c` 一致）：

1. **位 0 = 字节最高位**（`0x80 >> bit`），MSB-first；
2. 多字节整数为**小端**（`RS`/`RL`/`RD`）；
3. 每个原语都可能从**非字节边界**开始；
4. 越界读返回 0/空串，不 panic（解析不可信文件的底线）。

### 3.1 原语速查表

| 原语 | 含义 | 编码规则 |
| --- | --- | --- |
| `B` | 1 位布尔 | 直接读 1 位 |
| `BB` | 2 位 | 直接读 2 位 |
| `RC` | 1 字节 | 位对齐读 1 字节 |
| `RS` / `RL` | 2 / 4 字节整数 | 小端 |
| `RD` | IEEE-754 双精度 | 8 字节小端 |
| `BS` | 紧凑 16 位 | `BB` code：`0`→`RS`；`1`→`RC`；`2`→`0`；`3`→异常（返回 256） |
| `BL` | 紧凑 32 位 | R2000 下**就是 `RL`**（4 字节） |
| `BD` | 紧凑双精度 | `BB` code：`0`→`RD`；`1`→`1.0`；`2`→`0.0` |
| `BD1` | 默认 1.0 的紧凑双精度 | 同 `BD`（code 1 天然产出 1.0） |
| `BD0` | 默认 0.0 的紧凑双精度 | `0`→`0.0`；`1`→`1.0`；`2`→`0.0`；`3`→`RD` |
| `BT` | 厚度 | `B`：`1`→`0.0`；`0`→`BD` |
| `BE` |  extrusion 向量 | `B`：`1`→`(0,0,1)`；`0`→`3×BD` |
| **`DD(def)`** | **缺省双精度** | `0`→`def`；`3`→`RD`；`1`→**覆盖 `def` 低 4 字节**（顺序）；`2`→**保留高 2 字节、覆盖低 6 字节**（⚠️ 字节顺序是置换的 `[4,5,0,1,2,3]`，见第 8.4 节） |
| `MS` | 模块化短（对象大小） | 每 15 位一组，高位组带 `0x8000` 继续标志，最多 2 组 |
| `MC` | 模块化有符号字符 | 每字节 7 位有效，第 8 位为继续位，最多 5 字节 |
| `UMC` | 模块化无符号字符 | 同上但无符号，最多 8 字节 |
| `TV` | 字符串 | `BS` 长度 ＋ 字节（**无 codepage**） |
| `TU` | Unicode 字符串 | `BS` 长度 ＋ `2×len` 字节 UCS-2LE（R2007+ 用，本方案保留实现） |
| `TF(n)` | 定长二进制 | `n` 字节 |
| `H` | 句柄引用 | 见 [第 4 章](#第-4-章-句柄handle与双流模型) |
| `CMC` | 颜色 | R2000：单个 `BS` 索引（无真彩色） |

### 3.2 为什么要有 `DD`

DWG 的坐标压缩主要靠 `DD`：**相邻点只写入与前一个值不同的低字节**。
样例中 LWPOLYLINE 的 4 个顶点全部以 `2DD` 存储，只有首点是裸 `2RD`。这也解释了为什么
坐标解码容差能压到 `1e-9`：Delta 编码在写出端是按字节精确回写的，往返无损。

## 第 4 章 句柄（Handle）与双流模型

### 4.1 句柄的位编码 `read_h`

```text
RC code_byte  ──►  size = code_byte & 0x0F        // 后续字节数
                   code = (code_byte >> 4) & 0x0F // 引用类型
后随 size 个字节，按 **MSB-first** 累积成 value（大端！）
```

### 4.2 相对句柄解析 `resolve_handle`

句柄值可能是**相对引用**（相对引用者自身句柄），这是最容易踩的坑之一：

| code | 解析结果 |
| --- | --- |
| 6 | `own + 1` |
| 8 | `own - 1` |
| 10 | `own + value` |
| 12 | `own - value` |
| 14 | `own` |
| 其它（0/2/3/4/5） | `value`（字面值） |

```rust
fn resolve_handle(h: DwgHandle, own: u64) -> u64 {
    match h.code {
        6  => own.saturating_add(1),
        8  => own.saturating_sub(1),
        10 => own.wrapping_add(h.value),
        12 => own.wrapping_sub(h.value),
        14 => own,
        _  => h.value,
    }
}
```

### 4.3 双流模型（本方案的核心组织方式）

**同一个对象的数据被切成两条独立的位流**：

| 流 | 游标 | 内容 |
| --- | --- | --- |
| 字段流 `rd` | 对象数据起点 | type、bitsize、自身句柄、EED、几何/名称/标志等数值 |
| 句柄流 `hr` | `bitsize/8` 字节 `bitsize%8` 位 | owner、reactors、xdict、prev/next、layer、ltype、plotstyle… |

```rust
let mut rd = BitReader::at(obj_data, 0, 0);
let type_code = rd.read_bs();
let bitsize   = rd.read_rl() as usize;
let mut hr    = BitReader::at(obj_data, bitsize / 8, (bitsize % 8) as u32);
```

> **为什么必须分两条流**：句柄流长度取决于字段流里的标志位（如 `num_reactors`、`entmode`、
> `ltype_flags`），而字段流里的数值又可能被句柄流截断。把两者分开后，"字段读多少"和
> "句柄读多少"互不干扰，任何一侧读偏都不会污染另一侧 —— 这也是本方案能在几十处条件分支
> 下仍保持可维护的原因。

### 4.4 实体句柄流的固定条件顺序

`common_entity_handle_data.spec`（R2000 分支，即 `SINCE(R_2000b)`）：

```text
1. if entmode == 0              → ownerhandle
2. reactors × num_reactors
3. if !is_xdic_missing          → xdicobjhandle     ← R2004a+ 起是**条件**的（见 8.18）
4. if nolinks == 0              → prev_entity, next_entity  （仅 R13b1..R2000）
5. layer                        ← 我们真正要的
6. if ltype_flags == 3          → ltype
7. if material_flags == 3       → material          （SINCE R_2007a）
8. if shadow_flags == 3         → shadow            （SINCE R_2007a）
9. if plotstyle_flags == 3      → plotstyle
```

注意第 3 步：R2002 及以前无条件，R2004a 起由 `is_xdic_missing` 决定。R2007 下
`nolinks` 这一位被 `is_xdic_missing` 取代（都是 1 bit，宽度相同但语义不同），
且 R2007 **从不**输出 prev/next 链接。

`INSERT` 在以上之后**还多一个** `block_header` 句柄（`FIELD_HANDLE (block_header, 5, 0)`），
这是 INSERT 能反查块名的唯一线索。

## 第 5 章 三层业务解码：图层 / 几何 / 扩展属性

### 5.1 图层（类型码 `0x33`）

#### R2000（AC1015）字段流

`DWG_TABLE (LAYER)` + `COMMON_TABLE_FLAGS` 宏：

```text
字段流： num_reactors (BL≈BS)       ← 模块化 BL，值为 0 时只占 2 位
         name         (TV)
         is_xref_ref  (B)   is_xref_resolved (BS)   is_xref_dep (B)
         flag0        (BS)          ← SINCE(R_2000b)
         color        (CMC)         ← SINCE(R_13b1)
句柄流： owner(4)   reactors×num_reactors   xdict(3)
         xref(5)   plotstyle(5)   ltype(5)
```

#### R2007（AC1021）字段流 —— 顺序不同，且是三流并行的

关键差别来自 LibreDWG `decode.c` 的一处 `#include`：`common_object_handle_data.spec`
在 **`dwg_decode_object` 里、EED 之后、任何对象专属字段之前**被展开，而且它用的是**字段流**
`dat`（只有它后面的 `FIELD_HANDLE` 才走 `hdl_dat`）。所以"通用句柄数据"的两个**标量**
位次是**最前面的**，它们只是"管辖"后面的句柄，自己并不在句柄流上：

```text
字段流： num_reactors      (BL)     ← common_object_handle_data，最先！
         is_xdic_missing  (B)      ← SINCE(R_2004a)
         name             (T)      ← 字符串流，字段流一个 bit 都不消耗
         is_xref_resolved (BS)     ← R2004+ 只剩这一位标志
         flag0            (BS)
         color            (CMC)
句柄流： owner(4)  reactors×num_reactors  xdict(3)      ← 通用句柄数据，在 hdl_dat 上
         xref(5)  plotstyle(5)  material(5)  ltype(5)  ← LAYER 专属，紧随其后
字符串流：name（BS 长度 + UCS-2），位于 bitsize 之前、以 RS 尺寸标记 + has_strings 位收尾
```

为什么句柄流里 `owner/xdict` 排在 `xref` **之前**：`common_object_handle_data.spec` 在
`dwg_decode_object` 里执行（先），LAYER 专属的 `xref/plotstyle/material/ltype` 在
`dwg.spec` 的对象段执行（后）。句柄流是顺序消费的，于是就是这个次序。

位级实测（样例 `example_2007.dwg`，LAYER 句柄 `0x10`，`size = 35` 字节 = 280 bit）：

```text
bitsize = 170
字段流  60 → 127   num_reactors(BL)=0, is_xdic_missing(B)=0, is_xref_resolved=0,
                   flag0=1008, CMC(rgb=0xC3000007, flag=0)
字符串流 127 → 152  26 个 bit（data_size 是位数，不是字节数！）→ name "0"
尺寸标记 153 → 169   RS(26) + has_strings(1)
句柄流  170 → 274   owner=0x2, xdict=0x2B7, xref=0x0, plotstyle=0xF,
                   material=0x279, ltype=0x16；余 6 bit 为字节对齐填充
```

这 5 个句柄与 LibreDWG `dwgread` 导出的 DXF 逐项一致（`330→2`、`360→2B7`、`390→F`、
`347→279`、`6→Continuous`，Continuous 的句柄正是 `0x16`）。

`flag0` 位布局（`dwg.spec:3298`）：

| 位 | 含义 | 本方案字段 |
| --- | --- | --- |
| bit 0 | frozen | `frozen` |
| bit 1 | off | `off` |
| bit 2 | frozen in new viewports | `frozen_in_new` |
| bit 3 | locked | `locked` |
| bit 4 | plotflag | `plot_flag` |
| bit 5..9 | **线宽（5 位打包）** | `lineweight = (flag0 & 0x03E0) >> 5` |

> 样例 `flag0 = 0x03F0` → plotflag 置位、线宽 = **31**。
> ⚠️ 不要拿 DXF 的 `370 = -3`（Default）来"校验"它，那不是同一套编码，见 [8.5](#85-图层线宽是-5-位打包字段dxf-的-370-是另一套编码)。

### 5.2 图元几何

公共实体数据（`common_entity_data.spec`，R2000 分支）先读，产出决定句柄流形状的标志：

```text
preview_exists (B) → [可选 preview]
entmode        (BB)
num_reactors   (BS)     ← 紧凑 BS（ODA 的 "BB as BS" 怪癖，见 8.1）
nolinks        (B)      ← VERSIONS(R_13b1,R_2002)，R2000 有
color          (CMC)
ltype_scale    (BD1)
ltype_flags    (BB)
plotstyle_flags(BB)
invisible      (BS)
linewt         (RC)
```

随后按类型分派：

| 类型码 | 实体 | 字段流顺序（关键部分） |
| --- | --- | --- |
| `0x13` | **LINE** | `B z_is_zero` → `RD sx` → `DD ex(sx)` → `RD sy` → `DD ey(sy)` → [`RD sz`,`DD ez`] → `BT` → `BE` |
| `0x12` | **CIRCLE** | `3×BD` 圆心 → `BD` 半径 → `BT` → `BE` |
| `0x11` | **ARC** | `3×BD` 圆心 → `BD` 半径 → `BT` → `BE` → `BD` 起始角 → `BD` 终止角 |
| `0x1b` | **POINT** | `3×BD` → `BT` → `BE` → `BD` x 轴角 |
| `0x4d` | **LWPOLYLINE** | `BS flag(70)`；`flag&4→BD 宽度`；`&8→BD 标高`；`&2→BD 厚度`；`&1→3BD extrusion`；`BS num_points(90)`；`&16→BS num_bulges`；`&32→BS num_widths`；**顶点 `2DD` 向量**（首点裸 `2RD`，后续 `DD` 相对前一点）→ bulges → widths |
| `0x01` | **TEXT** | `RC dataflags`；`&1==0→RD 标高`；`2RD` 插入点；`&2==0→DD ax, DD ay`；`BE`；`BT`；`&4==0→RD 倾斜`；`&8==0→RD 旋转`；`RD` 高度；`&16==0→RD 宽度`；`TV value`；`&32/&64/&128==0→BS` |
| `0x07` | **INSERT** | `3×BD` 插入点 → `BB scale_flag` → 缩放三元组 → `BD` 旋转 → `3×BD` extrusion → `B has_attribs`；**再在句柄流上多读 1 个 `block_header` 句柄** |
| `0x1c` | **3DFACE** | `B has_no_flags` → `B z_is_zero` → `RD c1x` → `RD c1y` → [`RD c1z` 仅当 !z_is_zero] → `3×3DD` 相对前角点的 delta → [`BS invis(70)` 仅当 !has_no_flags] |
| `0x1f` | **SOLID** | `BT` 厚度 → `BD` elevation(38) → 4×`2RD` 角点（四角共享 elevation 为 z）→ `BE` extrusion |
| `0x20` | **TRACE** | 与 SOLID 字段流完全相同（`LATER_VERSIONS` 块），复用同一解码器，落到 `Geometry::Solid` |
| `0x23` | **ELLIPSE** | `3×BD` 圆心 → `3×BD` 长轴向量（相对圆心，即半长轴向量）→ `3×BD` extrusion → `BD` 轴比 → `BD` 起始参数 → `BD` 终止参数 |
| `0x2c` | **MTEXT** | `3×BD` 插入点 → `3×BD` extrusion → `3×BD` x_axis_dir → `BD` rect_width(41) → [`BD` rect_height(46)，`SINCE(R_2007a)`] → `BD` text_height(40) → `BS` attachment(71) → `BS` flow_dir(72) → `BD` extents_height → `BD` extents_width → **`T` 文本**(1) |
| `0x0f` | **POLYLINE_2D** | `BS flag(70)` → `BS curve_type(75)` → `BD` 起宽 → `BD` 终宽 → `BT` 厚度 → `BD` 标高(38) → `BE` extrusion → [R2004+ `BL num_owned` → 句柄流顶点向量 + seqend] |
| `0x10` | **POLYLINE_3D** | `RC curve_type(75)` → `RC flag(70)` → [R2004+ `BL num_owned` → 句柄流顶点向量 + seqend] |
| `0x1d` | **POLYLINE_PFACE** | `BS numverts(71)` → `BS numfaces(72)` → [R2004+ `BL num_owned` → 句柄流顶点向量 + seqend] |
| `0x1e` | **POLYLINE_MESH** | `BS flag(70)` → `BS curve_type(75)` → `BS num_m(71)` → `BS num_n(72)` → `BS m_density(73)` → `BS n_density(74)` → [R2004+ `BL num_owned` → 句柄流顶点向量 + seqend] |
| `0x0a` | **VERTEX_2D** | `RC flag(0)` → `3×BD` 点 → `BD` 起宽(40) → `BD` 终宽(41) → `BD` 凸度(42) → `BD` 切线角(50) |
| `0x0b` | **VERTEX_3D** | `RC flag(0)` → `3×BD` 点 |
| `0x0c` | **VERTEX_MESH** | `RC flag(0)` → `3×BD` 点 |
| `0x0d` | **VERTEX_PFACE** | `RC flag(0)` → `3×BD` 点（PFACE 的顶点；面索引另由 `0x0e` 携带） |
| `0x0e` | **VERTEX_PFACE_FACE** | `RC flag(=128)` → 4×`BSd` 顶点索引（**不是坐标**；索引指向 `0x0d` 顶点） |

> `POLYLINE_*` 与 `VERTEX_*` 的字段流顺序**随子类型而异**：2D 用 `BS`/ `BD`，3D 用 `RC`，PFACE/MESH 用 `BS` 计数；套错顺序会整段错乱并污染后续句柄（见 [8.24](#824-polyline-装配句柄向量优先顺序分组只是-r2000-回退)）。因此 `decode_polyline_header` 必须按 `0x0f/0x10/0x1d/0x1e` 分别实现，不能统一套一个模板。

#### 5.2.1 经典 POLYLINE 的"头部 + 顶点链"装配

DWG 不把多段线存成一条记录，而是拆成：

```text
POLYLINE_*  (头部对象，类型码 0x0f/0x10/0x1d/0x1e)
VERTEX_*    (顶点，0x0a/0x0b/0x0c/0x0d，N 个，紧跟头部或经句柄引用)
VERTEX_PFACE_FACE (0x0e，仅 PFACE：4× 索引，无坐标)
SEQEND      (0x06，终止符)
```

本方案分两步还原：

1. **解码阶段**（`decode_polyline_header` / `decode_vertex`）：头部只记录字段与——关键的——**顶点句柄向量**（`num_owned` 之后在句柄流上依次 `read_h` 读出的 `vertex_handles`）；每个 `VERTEX_*` 把点（与凸度）暂存到 `obj.vertex`；`0x0e` 只记 `face_indices`，**不**记点。
2. **装配阶段**（`assemble_polylines`）：
   * **主路径（句柄向量，R2004+ 权威）**：用 `handle_index` 把每个 `vertex_handles` 解析成对象下标，按序 stitch 到头部 `Geometry::Polyline`。这无论顶点在对象流里是否紧挨头部都成立。
   * **回退路径（顺序分组，仅 R2000）**：R2000 头部只带 first/last 句柄，没有完整向量，于是对"头部 → 中间 VERTEX → SEQEND"的连续片段做顺序分组。
   * `VERTEX_PFACE_FACE`（0x0e）在装配时被**跳过**（只有索引，没有点）。

> ⚠️ **句柄向量陷阱**：在 `example_2007.dwg` 里，POLYLINE_3D（#263）的 `SEQEND` 排在了 4 个 `VERTEX_3D` **之前**（流顺序：#263 头部 → #264 SEQEND → #265–268 VERTEX）。纯按"头部后连续 VERTEX"的顺序分组会**装配出 0 个顶点**——只有句柄向量能权威还原。这正是必须首选句柄向量、顺序分组仅作 R2000 回退的原因。

`INSERT` 的 `scale_flag` 编码（`dwg.spec:735`）：

| scale_flag | 缩放读取方式 |
| --- | --- |
| 3 | `(1.0, 1.0, 1.0)`，不存数据 |
| 1 | x = 1.0（不存），y/z = `DD(1.0)` |
| 2 | `RD s`，y = z = s |
| 0 | `RD sx`，y = `DD(sx)`，z = `DD(sx)` |

### 5.3 扩展属性（本项目的重点）

DWG 里"扩展属性"其实是**两套完全不同的东西**，混为一谈是最常见的误解：

| 维度 | **EED**（Extended Entity Data） | **XData**（Xrecord 数据） |
| --- | --- | --- |
| 挂在谁身上 | **任意对象**（尤其是实体） | `XRECORD` 对象（`0x4f`） |
| 二进制位置 | 对象自身句柄**之后**、正式字段之前 | XRECORD 的字段流中部 |
| 结构 | `BS size` → `H appid` → size 字节数据项链；`size==0` 结束 | `BS num_reactors` → `BS xdata_size` → resbuf 链（`RS` 组码 + 载荷）→ `BS cloning(280)` |
| 组码 | 内部 code `0..71` | **标准 DXF 组码**（1/10/40/70/102/280/340…，范围远宽于 1000..1071） |
| LibreDWG 解码器 | `dwg_decode_eed` / `dwg_decode_eed_data` | `dwg_decode_xdata`（签名只接受 `Dwg_Object_XRECORD*`） |

> **重要结论**：LibreDWG 的 `dwg_decode_xdata` 只服务 XRECORD，说明"挂在实体上的扩展数据"
> 在二进制里就是 **EED 链**。本方案对**每一个对象**（不只实体）都解 EED，因此在扩展属性覆盖上
> **没有盲区**。

**EED 内部数据项 code：**

| code | 载荷 |
| --- | --- |
| 0 | 字符串：`RC len` + `RS_BE codepage` + len 字节 |
| 1 | `RS` appid 索引 |
| 2 | `RC` close/open 标志 |
| 3 | `RLL` 图层句柄（8 字节小端） |
| 4 | 二进制块：`RC len` + len 字节 |
| 5 | **实体句柄（`RLL_BE`，8 字节大端）** |
| 10..15 | 3×`RD` 点 |
| 40..42 | `RD` 实数 |
| 70 | `RS` 短整型 |
| 71 | `RL` 长整型 |

**XData 组码 → 值类型**（`dwg_resbuf_value_type`，`src/xdata.rs::resbuf_value_type` 完整转录）：

| 组码区间 | 类型 |
| --- | --- |
| 0..4, 6..9, 100..102, 300..309, 419..429, 439..479, 1000..1009 | `String` |
| 5, 105, 320..329, 390..399, 1005；以及 `gc < 0` | `Handle` |
| 10..37, 110..139, 210..269, 1010..1039, 1043..1069 | `Point3` |
| 38..59, 140..149, 460..469, 1040..1042 | `Real` |
| 70..79, 170..179, 270..279, 370..389, 400..409, 1070 | `Int16` |
| 90..99, 410..429, 440..459, 1071 | `Int32` |
| 160..169 | `Int64` |
| 280..289 | `Int8` |
| 290..299 | `Bool` |
| 310..319, 1004 | `Binary` |
| 330..369 | `ObjectId` |
| 106..109, 180..209, 480..998，以及 >1071 | `Invalid`（遇到即终止该链） |

> 完整边界见源码；关键是**它接受普通 DXF 组码**，不要按"实体 XData 只允许 1000..1071"的直觉去裁剪。

### 5.4 块与 INSERT 的二次解析

二进制里 **INSERT 只存 `BLOCK_HEADER` 句柄**，块名在另一条记录里。流程：

1. 解 `BLOCK_HEADER`（`0x31`）时，只读 `num_reactors(BS)` + `name(TV)` 就**停手**
   （后面的 `base_pt`/`xref_pname`/`num_inserts`/`description`/`preview` 与命名无关，
   跳过可规避版本差异带来的字段漂移）；
2. `parse_file` 汇总成 `HashMap<handle, name>`；
3. `resolve_insert_block_names` 把名字回填到 `Geometry::Insert.block_name`。

## 第 8 章 已知坑位与规避方法

> 这一章是"用时间与二进制位数换来的"。每一条都给出**现象 → 根因 → 规避**。

### 8.1 `num_reactors` 是**模块化** `BL`，不是 4 字节 `RL`

* **现象**：读 LAYER/实体时后续字段全部错位，名字变成乱码。
* **根因**：`FIELD_BL (num_reactors, 0)` 在 LibreDWG spec 里挂着注释
  *"ODA bug: BB as BS"* —— 磁盘上用的是 2 位 code（值为 0 时**只占 2 位**），不是 4 字节。
* **规避**：`let num_reactors = rd.read_bl();`，而 `read_bl` **必须是模块化的**
  （见 [8.16](#816-bit_read_bl-是模块化的不是裸-4-字节-rl)）。**同理** `LWPOLYLINE` 的
  `num_points`（按裸 `RL` 读会得到 3089706561，按模块化读才是 4）与 `XRECORD` 的
  `num_reactors`/`xdata_size` 也都是紧凑编码。
* **通判**：DWG 里"小整数计数"几乎一律带 2 位 code 前缀。

> 历史上这里写的是"用 `read_bs`"。结论没错（结果正确），理由不准确：`BS` 与模块化 `BL`
> 在 `0..=255` 区间**逐位相同**（code 2 / code 1+RC），只有 `> 255` 时才分叉（`RS` vs `RL`）。
> 真正致命的是把 `BL` 当成**裸 4 字节 `RL`** 来读。

### 8.2 句柄段里的偏移是**绝对文件偏移**，不是相对段偏移

* **现象**：对象全部解析为空 / size 校验失败。
* **根因**：`offset` 是 `MC`（**有符号增量**），必须累加到 `last_offset` 上，且 `last_offset`
  是全局累积的（跨页不清零）。
* **规避**：用 `i64` 累加，只在 `0 < last_offset < file.len()` 时收留；页循环前后不要重置。

### 8.3 相对句柄：code 6/8/10/12/14

* **现象**：图层句柄、`XData` 组 340 的句柄"像是对的但差一点点"。
* **根因**：句柄值可能是相对引用者自身句柄的偏移（`dwg_decode_handleref`）。
* **规避**：**任何从流里读出的句柄都要过 `resolve_handle(h, own_handle)`**；直接拿 `h.value`
  当绝对句柄用，在样例文件里会错。

### 8.4 `DD` 是字节覆盖，且 mode 2 的覆盖顺序是**置换的**而非顺序填充

* **现象**：短 LINE / 多段线顶点 delta 小时一切正常，但**长 LINE 的终点**系统性偏差几十到几百个单位（如 `end.x` 比真值大 85、205），而起点（裸 `RD`）始终精确；ARC 角度的"差 0.02°"其实只是 double 精度的舍入噪声，并非此处问题。
* **根因**：`bit_read_DD(def)` 的语义是
  `0 → def`；`3 → RD`；`1 → 覆盖 def 低 4 字节`；`2 → 保留 def 高 2 字节（索引 6,7）、覆盖低 6 字节`。它本身是**字节级拼装**，不是 `def + delta`。
  **真正的陷阱在字节顺序**：Encoder（`bit_write_DD`，小端分支）对 mode 2 写出的低 6 字节顺序是
  `[byte4, byte5, byte0, byte1, byte2, byte3]`，Decoder 必须把流字节**散射回填**到双精度字节索引
  `{4,5,0,1,2,3}`，**而不是** `db[0..6] = stream[0..6]` 的顺序填充。后者等于把字节序整体反转，
  会静默摧毁所有"低 6 字节与 `def` 不同"的 `DD` 值——恰恰就是 `LINE` 的 `end.x/end.y`
  （相对 `start` 的 `DD`，线一长低 6 字节就与 `start` 分叉）。mode 1（低 4 字节）才是顺序
  `[0,1,2,3]`，二者**不可混为一谈**。多段线顶点因 delta 小多用 mode 1，所以这一 bug 一度没暴露。
* **规避**：`read_dd` 的 mode 2 分支按 `b4,b5,b0,b1,b2,b3` 顺序取 6 个 `RC` 并填回
  `db[4],db[5],db[0],db[1],db[2],db[3]`，保留 `def` 的 `db[6..8]`；mode 1 才是
  `db[0..4] = stream[0..4]`。单元测试 `dd_uses_two_bit_code_with_default` 已按 LibreDWG 的写出顺序构造
  流并断言逐位还原。修复后 R2007 全部 68 条 LINE 与真值 DXF 逐端点集合匹配（容差 `1e-2`），0 处不符。

### 8.5 图层线宽是 5 位打包字段，DXF 的 370 是另一套编码

* **现象**：`flag0 = 0x03F0` 解出线宽 31，DXF 里却是 `370 = -3`，"解析错了"。
* **根因**：`lineweight = (flag0 & 0x03E0) >> 5` 是 0..31 的索引；DXF 的 `370` 用
  `-3 = Default`、`-1 = ByLayer`、`-2 = ByBlock`。两者不经过同一套换算。
* **规避**：**不要用 DXF 的 370 去"纠正"二进制解出的 31**。31 才是正确的二进制解码值。

### 8.6 类型码不要照抄 ODA 文档

* **现象**：`0x36/0x37` 查不到任何对象，LTYPE 解析不到。
* **根因**：R2000 的实际编码与经典 ODA 文档不同，LibreDWG 的 `dwg.spec`/`dwg2.spec` 才是真值
  （以声明前的 `/* (code) */` 注释为准）。
* **规避**：已修正并写进 `type_name` 的注释：

  | 码 | 正确类型 | 常见误标 |
  | --- | --- | --- |
  | `0x04` / `0x05` | BLOCK / ENDBLK | UNKNOWN |
  | `0x31` | **BLOCK_HEADER** | BLOCK |
  | `0x34` | STYLE_CONTROL | STYLE |
  | `0x1c` / `0x1d` | 3DFACE / POLYLINE_PFACE | ATTRIB / ATTDEF |
  | `0x38` / `0x39` | **LTYPE_CONTROL / LTYPE** | 0x36/0x37 |
  | `0x44` | DIMSTYLE_CONTROL | LTYPE |
* **通判**：类型码错标**不会报错**，只会静默产出垃圾。务必用 [7.3](#73-一个决定性的调试工具对象类型直方图) 的直方图核对。

### 8.7 "实体级 XData"其实不存在：EED 与 XData 是两套东西

* **现象**：在实体里找 1000..1071 组码一无所获，以为扩展数据丢了。
* **根因**：LibreDWG 的 `dwg_decode_xdata` 签名只接受 `Dwg_Object_XRECORD *`；挂在实体上的
  扩展数据在二进制里是 **EED 链**，位于对象自身句柄之后。
* **规避**：两者都读、都暴露（`ParsedObject.eed` 与 `ParsedObject.xdata`）。**不要用
  "XData 只允许 1000..1071"的直觉去过滤 XRECORD 数据**——它用的是普通 DXF 组码（1/10/40/70/102/280/340…）。

### 8.8 块名：二进制里第二个图纸空间仍叫 `*Paper_Space`

* **现象**：解析出 `*Model_Space / *Paper_Space / *Paper_Space`，而 DXF 里是
  `*Model_Space / *Paper_Space / *Paper_Space0`，怀疑解码少读一个字符。
* **根因**：逐位核对过：TV 长度字段是 `0x0C = 12`，12 字节正好是 `*Paper_Space`，**没有结尾 `0`**。
  是 LibreDWG 导出 DXF 时为去重给第二个补了 `0`。
* **规避**：以**二进制为准**修正测试期望，而不是改解析器。教训：出现"差一个字符"时先数长度字段。

### 8.9 CRC / 页边界必须字节对齐

* **现象**：读了几页之后偏移全乱。
* **根因**：页内条目是位流，页尾的 `RS_BE` CRC 是**字节对齐**的，未对齐就跳过一字节。
* **规避**：`if r.bit > 0 { r.byte += 1; r.bit = 0; }` 后再读 CRC。

### 8.10 不可信长度/计数的死循环与越界

* **现象**：一个损坏文件导致挂死或 OOM。
* **根因**：`xdata_size`、`num_points`、`num_reactors` 都可能因误解析而变成天文数字。
* **规避**：本方案的三道闸门 ——
  1. `xdata_size.min(hs_byte - rd.byte)`（绝不越过句柄流起点）；
  2. `num_reactors.min(1_000_000)`、`num_points <= 20_000`（LibreDWG `VALUEOUTOFBOUNDS` 同款上限）；
  3. 循环中检测 `r.byte == oldpos`（无进展）立即 `break`。
* **通判**：解析器面对的是不可信输入，**任何循环都必须有"无进展即退出"的兜底**。

### 8.11 `MS` 的大小端与 `MC` 的符号

* **现象**：对象 `size` 读到巨大值，或偏移增量变负却当正数用。
* **根因**：`MS` 的每个 15 位字是**大端**读出；`MC` 是**有符号**模块化字符（7 位/字节，第 8 位为继续位）。
* **规避**：`read_ms` 用 `read_rs()`（大端），`read_mc` 返回 `i64` 并处理 `0x40` 符号位。

### 8.12 字符串：`TV` 不是 `TU`，R2000 无 codepage

* **现象**：中文/Unicode 文本乱码，或字符串长度错位。
* **根因**：R2000 用 `TV = BS 长度 + 字节`（**无 codepage**）；`TU`（UCS-2LE）是 R2007+ 才有。
  EED 的 code 0 字符串则**有** `RS_BE` codepage。
* **规避**：R2000 路径一律 `read_tv`；EED 内严格按 `RC len + RS_BE codepage` 读；
  `read_tv` 中把长度 clamp 到剩余缓冲并去掉结尾 NUL。

### 8.13 句柄字节是大端，与整数的小端相反

* **现象**：句柄值看着"位反转"。
* **根因**：`read_h` 的 `size` 个字节是 **MSB-first** 累积，而 `RS/RL/RD` 是小端。
* **规避**：`value = (value << 8) | byte`，不要与其他整数原语共用一套字节序直觉。

### 8.14 版本闸门要前置（现已放行 AC1015 与 AC1021/AC1024/AC1027/AC1032）

* **现象**：拿不支持的版本来解析，得到一堆看似合理实则错误的数据；更常见的是**报错信息指向
  错误的方向**（AC1018 曾报 `decompression error: offset underflow`，真因是容器选错）。
* **根因**：R2007+ 的段是内存映像，需 RS 去交织与 LZ77 解压；字符串走独立的 UCS-2
  字符串流；数据页头还有 `0x4164536b ^ address` XOR 掩码。而且**容器不止一种**——R2004 的
  `AcFssFcAJMB` 段树与 R2007 的页容器毫无共同点。拿错档去解必然产出垃圾。
* **规避**：`parse_file` 第一时刻校验 `file[0..6]`，放行 `AC1015`（2000–2002）、
  `AC1018`（2004–2006，段树）、`AC1021`（2007–2009，页容器）与
  `AC1024/AC1027/AC1032`（2010–2024，**含 CAD 2020**，段树），
  其余一律返回错误。**永远不要**对不支持的版本"尽力解析"——这是 AC1037（AutoCAD 2024+，未实测）
  被拒绝而不是硬解的原因。
* **注意**：闸门放行 ≠ 实测通过。现在 AC1015 / AC1018 / AC1021 / AC1024 / AC1027 / AC1032
  六档**都有真实样本**，并与 LibreDWG 的 `dwg2dxf` 导出做了 14 类实体的逐字段交叉核对
  （`tests/crosscheck_geom.py`，六档全过，最大偏差 5.1e-11）。AC1037 仍无样本，保持拒绝。

### 8.24 POLYLINE 装配：句柄向量优先，顺序分组只是 R2000 回退

* **现象**：`POLYLINE_3D`（#263）按"头部后连续 VERTEX"顺序分组，得到 **0 个顶点**。
* **根因**：在该文件里 `SEQEND`（#264）排在 4 个 `VERTEX_3D`（#265–268）**之前**——对象流的
  物理顺序不是"头部→顶点→SEQEND"。经典 POLYLINE 的顶点要么紧邻头部，要么只经句柄引用，
  两者都可能。
* **规避**：`decode_polyline_header` 在 R2004+ 读 `num_owned(BL)` 后，从句柄流依次 `read_h`
  捕获 `vertex_handles`；`assemble_polylines` **首选用句柄向量**装配（对顶点位置不敏感），
  仅在 R2000（只有 first/last 句柄、无完整向量）才退化到顺序分组。装配后把已解析的 POLYLINE
  从回退集合里移除，避免空列表覆盖正确顶点。
* **附带陷阱**：`VERTEX_PFACE_FACE`（0x0e）携带的是 4×`BSd` **面索引**，不是坐标——读取时
  若当成 `3BD` 会污染整段；装配时也必须跳过它。`POLYLINE_*` 头部字段顺序随子类型不同
  （2D 用 `BS`/`BD`，3D 用 `RC`，PFACE 用 `BS` 计数），套错模板会整段错位并污染后续句柄。

### 8.15 工具层面的坑：CRLF

* **现象**：`grep '^AcDbLine$' sample_2000.dxf` 匹配不到任何东西。
* **根因**：DXF 参照文件是 CRLF。
* **规避**：先 `tr -d '\r' < sample_2000.dxf > s.dxf` 再做行锚定匹配。

### 8.16 `bit_read_BL` 是模块化的，不是裸 4 字节 `RL`

* **现象**：R2007 的 LAYER 全线错位——`flag0` 得到 30 而非 1008，颜色得到 256 而非 7，
  句柄流读出 `owner = 0x1EA4`、`num_reactors = 1354170930` 这种天文数字。
* **根因**：LibreDWG `bits.c` 的 `bit_read_BL` 与 `bit_read_BS` 一样带 2 位 code：

  | code | 语义 | 占用 |
  | --- | --- | --- |
  | `00` | `RL`（4 字节小端） | 2 + 32 bit |
  | `01` | `RC`（1 字节） | 2 + 8 bit |
  | `10` | **0** | **仅 2 bit，无负载** |
  | `11` | 256（错误哨兵） | 2 bit |

  把它实现成裸 `read_rl()` 会在每个"值为 0"的 `BL` 上多吃 32 bit。
* **规避**：`read_bl` 一律走 code 分支。`bit_write_BL` 对称地只对 `0` 写 `BB(2)`，
  所以文件里"全零计数"真的只有 2 bit。
* **附带结论**：`BS` 与模块化 `BL` 在 `0..=255` 上逐位相同，混淆二者无害；
  混淆 `BL` 与 `RL` 是灾难。

### 8.17 R2007 的 `num_reactors` / `is_xdic_missing` 在**字段流**上，且排在最前

* **现象**：LAYER 的 `flag0` 差 3 bit（读到 30 而不是 1008），并且怎么挪都对不上。
* **根因**：`decode.c` 的 `dwg_decode_object` 在 EED 之后直接
  `#include "common_object_handle_data.spec"`，此时 `dat` 仍是**字段流**。里面前两项是
  `FIELD_BL(num_reactors)` 与 `SINCE(R_2004a) FIELD_B(is_xdic_missing)`，之后才轮到对象
  专属字段；只有 `ownerhandle / REACTORS / XDICOBJHANDLE` 这三个 `FIELD_HANDLE` 走 `hdl_dat`。
* **规避**：对象的解码顺序是
  `num_reactors(BL) → is_xdic_missing(B) → name(T) → 对象专属字段`，
  不要把它塞到句柄流开头去读。
* **代价**：最常见的 `num_reactors == 0` 恰好就是 **3 bit**（2 + 1）。少读这 3 bit，
  `flag0`、CMC 的 `rgb`、字符串流起点会一起平移。

### 8.18 `xdict` 句柄是**条件**的（`is_xdic_missing` 为 1 时不存在）

* **现象**：实体的 `layer` 解析成 `?`（句柄为 0 或指向错误对象）。
* **根因**：`dec_macros.h` 里 `ENT_XDICOBJHANDLE(code)` / `XDICOBJHANDLE(code)` 的实现是
  `SINCE(R_2004a) { if (!is_xdic_missing) { 读句柄 } }`。无条件地读它，会把 `layer`
  及之后的所有句柄整体前移一格。
* **规避**：`if !f.is_xdic_missing { hr.read_h(); }`。`is_xdic_missing` 是
  `common_entity_data.spec` / `common_object_handle_data.spec` 里那个 1 bit。
* **实测**：修正后 `example_2007.dwg` 的 143 个图元，`(类型, 图层名)` 二元组与 DXF 真值
  **逐项一致，0 处不符**。

### 8.19 值为 0 的句柄只写 `code << 4` **一个字节**

* **现象**：句柄流里冒出一个"多余"的 `(5, 0)`，被误判成多读了一个字段。
* **根因**：`bit_write_H` 对 `value == 0` 只输出 `code << 4`（size = 0，无负载字节）。
* **规避**：LAYER 句柄流里的 `(5, 0)` 就是 `xref`（code 5，值 0）——不是多余的 reactor，
  也不是数错了。它出现在 `xdict(3)` 之后、`plotstyle(5)` 之前。

### 8.20 CMC 的 `rgb` 低 24 位**可能是 ACI 索引，不是调色板 RGB**

* **现象**：`rgb = 0xC3000007`，按调色板反查返回 256（无匹配），但 DXF 里 `62 → 7`。
* **根因**：真实文件把普通索引色写成 `method << 24 | index`（`method = 0xC3`）。
  而 LibreDWG 的 `dwg_find_color_index` 只做 24 位 RGB 精确匹配，必然失配——
  它自己在 `bit_downconvert_CMC` 里给了兜底：

  ```c
  index = dwg_find_color_index (color->rgb);
  if (color->index == 256)
    color->index = color->rgb & 0xff;
  ```

* **规避**：用 `cmc_color_index(rgb)`——先调色板匹配，失配则回退 `rgb & 0xff`；
  `method` 为 `0xC0/0xC1/0xC8` 时直接给 256 / 0 / 0。
* **实测**：三个图层 `0xC3000007 → 7`、`0xC3000002 → 2`、`0xC3000004 → 4`，
  与 DXF 的 `62` 完全对上。（若按 `RGB_PALETTE` 去存，这三个值应是
  `0xFFFFFF` / `0xFFFF00` / `0x00FFFF`——不是。）

### 8.21 R2007 的**实体** `T` 字段也在字符串流里

* **现象**：TEXT 的值解出 `鹀Ḁ਀` 这类乱码；而另一个 TEXT 恰好是对的（因为它的字段流
  恰好落在字符串流区域），极易误判为"已修好"。
* **根因**：R2007 把**对象与实体**的所有 `T` 字段统一放进该对象的字符串流；只有 R2000
  才是字段流上的 inline `TV`。
* **规避**：`read_t(rd, str_rd, dialect, dialect == Dialect::R2007)`——按方言选流，
  别写死 `true` / `false`。写死 `true` 会让 R2000 的所有对象名变成空串
  （R2000 没有字符串流，`None` 直接返回 `""`）。
* **实测**：修正后两个 TEXT 分别得到 `"teksto simpla"` 与 `"xx"`，与 DXF 一致。

### 8.22 字符串流的 `data_size` 是**位数**，不是字节数

* **现象**：`setup_string_stream` 算出起点后越界（回退到缓冲区之前）而返回 `None`。
* **根因**：`obj_string_stream` 的 `bit_advance_position(-data_size)` 里 `data_size`
  是 bit 计数。样例 LAYER 的 26 表示 **26 bit**（`BS` 长度 + 1 个 UCS-2 单元），
  不是 26 字节——后者会让光标退到对象开头之前。
* **规避**：按位回退，并用 `pos < 0` 兜底返回 `None`。

### 8.23 `flag0` 是内部位掩码，不要拿 DXF 的 `70` 去"校验"

* **现象**：`flag0 = 1008`，DXF 里 `70 → 0`，看起来"差得离谱"。
* **根因**：`70` 只承载冻结/关闭/锁定等**真值**；而 `flag0` 还打包了 plotflag 与 5 位线宽。
  `1008 = 0x3F0` = plotflag(bit4) + lineweight `31`(bits 5..9)，其余位为 0——
  与 `70 → 0` 完全自洽。
* **规避**：见 [8.5](#85-图层线宽是-5-位打包字段dxf-的-370-是另一套编码)；
  判断"解对了没有"要看 `owner/xdict/plotstyle/material/ltype` 句柄是否与 DXF 对齐。

### 8.25 EED 解码循环必须保证游标推进

* **现象**：一张经位翻转的损坏 R2007 文件让解析器**内存爆炸被 SIGKILL**（不是报错，是 OOM），
  调用栈停在 `xdata::decode_eed` 分配 2 GiB。`tests/robustness.rs` 的位翻转模糊测试抓到了它。
* **根因**：`decode_eed` 的主体是 `while r.byte < end { ... }`，但循环体里的字段读取在**越界时
  返回 0 且不推进游标**（`BitReader` 的安全读行为）。一旦 `end` 指向缓冲区之外，游标永远到不了
  `end`，循环变成死循环，每次迭代 `items.push(...)` 一个 `(0,None)` 直到堆耗尽。
* **规避**：`BitReader` 新增 `at_end()`；`decode_eed` 在循环顶部改判 `!r.at_end() && r.byte < end`，
  并在每次 `decode_eed_item` 返回 `None` 时 `break`。配套在 `parse_object` 入口加 `at_end()` 守卫，
  避免对象层对越界对象缓冲反复下钻。**原则**：任何 `while cursor < end` 循环都必须有"游标严格
  单调前进"或"到达缓冲末尾即停"的保证，否则恶意/损坏输入能把它变成分页炸弹。

## 第 9 章 已知限制与演进路线

### 9.1 当前限制

| 限制 | 影响 | 备注 |
| --- | --- | --- |
| ~~R2007/R2010+ 仍会失败~~ **已解除** | — | 现已支持 AC1015（2000–2002）与 AC1021/AC1024/AC1027/AC1032（2007–2024），见 0.2 |
| **AC1018（R2004）支持** | 该类文件正常解析 | 已实现 `decode_R2004` 段树容器；AC1024/1027/1032 复用同一容器，见 0.2 |
| AC1037（AutoCAD 2024+）不支持 | 该类文件直接返回错误 | 更新格式，无实测样本；拒绝优于猜测解析 |
| 除 AC1015/AC1021 外无真值样本 | AC1024/1027/1032 的几何正确性部分来自"容器字节兼容"论证 | 见 8.14；但 **XData 真值已覆盖全部六档**——`tests/xdata.rs` 用 LibreDWG `dwgread -v4` 的字段级 trace 逐 release 比对 |
| 未实现的实体 | DIMENSION 系列、SPLINE、HATCH、MLINE、LEADER、ATTRIB 等只保留句柄与 EED | 不影响图层/扩展属性；**ELLIPSE / 3DFACE / SOLID / TRACE / 经典 POLYLINE+VERTEX / MTEXT 均已实现** |
| `VERTEX_*` 不作为独立实体暴露 | `entities()` 里看不到顶点 | 顶点已按句柄向量装配进所属 `POLYLINE` 的 `vertices` |
| POLYLINE 的**面拓扑**未输出 | PFACE 的 `VERTEX_PFACE_FACE` 索引（71–74）已解码但未组装成面表 | 若需要三角网格，可在 `VertexData::face_indices` 上继续拼装 |
| EED 条目比 DXF 真值多 1 个应用块 | 扩展属性计数不完全对齐 | 样例文件 36 vs 35，疑似某个对象上的 EED 边界多解出一项；待定位 |
| 无块层级树 | 无法通过 BLOCK 引用递归展开嵌套图元 | 需 owner 链 |
| 无坐标系/视口变换 | 输出的是图元自身坐标（OCS/WCS 未区分） | 多数 GIS/提取场景够用 |
| 未解析样式表细节 | STYLE/LTYPE/DIMSTYLE 只保留句柄与 EED | — |
| XData 未按 appid 归并 | 返回的是扁平 resbuf 链 | 上层可自行按 1001 分组 |

### 9.2 演进路线

1. ~~**补齐实体类型**~~ **阶段性完成**：ELLIPSE / 3DFACE / SOLID / TRACE /
   **经典 POLYLINE（2D/3D/MESH/PFACE）+ VERTEX 链装配** / **MTEXT**
   全部落地并逐字段通过真值 DXF 核对（偏差 ~1e-11；MTEXT 的文本字符串逐字符一致）。
   下一步：SPLINE、DIMENSION 系列；
2. **构建 owner 链**：用句柄流里的 owner 句柄串成"块 → 图元"树，支持块嵌套与属性（ATTRIB）提取；
3. **XData 按 appid 分组**：以组码 1001 为分隔把 `Vec<XDataItem>` 组织成
   `HashMap<appid, Vec<XDataItem>>`；
4. ~~**R2004/2007 支持**~~ **已完成**：页容器（AC1021，LZ77 + Reed–Solomon 解交织）与
   段树容器（AC1018，XOR 头 + ACD）两套都实现；`TU` 字符串流、模块化 `BL`、条件句柄、
   `EntityVariant` 版本闸门均已落地。在此基础上
   **AC1024(2010–2012) / AC1027(2013–2017) / AC1032(2018–2024)** 也一并支持
   ——因为它们复用 AC1018 的段树容器（其中 AC1032 即 AutoCAD 2020 写出的格式）；
5. ~~**R2004（AC1018）支持**~~ **已完成**：`AcFssFcAJMB` 段树容器已实现，真实样本
   `tests/data/example_2004.dwg` 已通过 LibreDWG 真值交叉核对；
6. **并行解析**：对象相互独立（见 2.4），可在 `std::thread` 上按偏移分片并行，零依赖下也能做。
